# 🚀 Cassandra Framework
## Техническое задание: Страница Login Page (Авторизация)

### 📌 Обозначения
-   **`ElementName`** *(type)* — UI-элемент с указанием типа
-   *"Text content"* — отображаемый текст на интерфейсе
-   `code` — технические термины, классы, методы
-   ⚠️ *(decorative)* — декоративный элемент, не подлежит автоматизированному тестированию

## 1. 🎯 Назначение
Центральный экран аутентификации для доступа к системе оценки колонизации планет. Обеспечивает ввод учётных данных, клиентскую валидацию и передачу данных в сервис авторизации.

## 2. 🖥️ Элементы интерфейса

### 2.1 Основные элементы формы

-   **`Brand Title`** *(text)* — Заголовок "CASSANDRA" со стилизованным суффиксом. *"CASSAN"* отображается белым шрифтом, *"DRA"* имеет голубое свечение.

-   **`Subtitle`** *(text)* — Статичная подпись под заголовком. Текст: *"Access to Colonization Assessment System"*.

-   **`Auth Error Block`** *(alert)* — Блок ошибки авторизации. Отображается над формой при неуспешной аутентификации. Текст: *"⚠️ Invalid callsign or access code"*. По умолчанию скрыт.

-   **`Callsign`** *(input)* — Поле ввода позывного исследователя. Placeholder: *"Enter callsign"*. Максимальная длина: 100 символов. Допустимые символы: буквы (латиница), цифры, спецсимволы.

    -   *Реализация валидации:* Клиентская проверка на уровне UI. Ограничение длины enforced через HTML-атрибут `maxlength`. Ввод кириллицы блокируется через JS.

-   **`Access Code`** *(input)* — Поле ввода ключа доступа. Placeholder: *"Enter access code"*. Максимальная длина: 30 символов. Допустимые символы: **буквы (латиница), цифры и нижнее подчеркивание (`_`)**.

    -   *Реализация валидации:* Клиентская проверка на уровне UI. Тип поля `type="password"`. Фильтрация невалидных символов enforced через JS (`replace(/[^a-zA-Z0-9_]/g, '')`) и атрибут `inputmode="text"`.

-   **`Toggle Password Button`** *(button)* — Кнопка переключения видимости ключа доступа. Расположена внутри поля `Access Code` справа. Содержит SVG-иконку глаза (открытый/закрытый). При нажатии переключает тип поля между `password` и `text`.

-   **`Establish Connection`** *(button)* — Кнопка подтверждения входа. Label: *"Establish Connection"*. Состояние: неактивна (`disabled`), пока поле `Callsign` не содержит ≥ 3 символов, а поле `Access Code` не содержит ≥ 4 символов.

-   **`Lost Access Text`** *(text)* — Информационный текст-подсказка. Label: *"Lost access code?"*. Не является интерактивным элементом (не кнопка, не ссылка). Отображается приглушенным цветом.

-   **`Restore Clearance`** *(link)* — Ссылка восстановления доступа. Label: *"Restore clearance"*. Визуально оформлена как кнопка с рамкой. 

-   *Поведение:* При клике происходит переход на страницу восстановления пароля (`forgot-password.html`). Это действие доступно в любой момент и не зависит от состояния формы авторизации.

### 2.2 Декоративные элементы ⚠️

> **Примечание:** Элементы данного раздела являются частью визуального оформления страницы и **не подлежат автоматизированному тестированию**. Они не имеют `data-wm-id` и не включаются в CAS-сценарии.

-   **`Satellite`** *(decorative/svg)* — Летающий спутник с солнечными панелями и антенной. Перемещается по экрану с отталкиванием от границ окна браузера (эффект "DVD-логотипа"). От спутника каждые ~2 секунды расходятся три радиоволны (анимированные SVG-круги), символизирующие поиск сигнала. Проходит за формой авторизации (z-index ниже карточки), создавая эффект "мёртвой зоны".

-   **`Stars Background`** *(decorative/css)* — Анимированный фон со звёздами и Млечным Путём.

### 2.3 Служебные элементы

-   **`Telemetry`** *(text)* — Строка состояния системы в футере. Отображается моноширинным шрифтом с мигающим курсором (`█`). 

    -   Состояние по умолчанию (до авторизации): *"> SYSTEM READY. AWAITING CONNECTION"* (синий цвет, rgb(77, 166, 255) / #4da6ff).

    -   Состояние после успешной авторизации: *"> CONNECTION ESTABLISHED. WELCOME, {ROLE} {FULL_NAME}"* (зелёный цвет,rgb(46, 204, 113) / #2ecc71).

    -   Состояние после неуспешной авторизации: *"> SYSTEM FAILURE. INVALID CREDENTIALS"* (красный цвет, rgb(231, 76, 60) / #e74c3c).

-   **`Footer Brand`** *(text)* — Копирайт в футере. Текст: *"Evknopia © 2026"*.

## 3. ✅ Правила валидации

-   **`Callsign`**: 
    -   Минимальная длина — 3 символа. 

    -   Поведение: Пока не введено минимум 3 символа, кнопка **`Establish Connection`** физически неактивна 
    (`disabled`). Ошибки под полем не отображаются.

-   **`Access Code`**: 
    -   Минимальная длина — 4 символа. 

    -   Поведение: Пока не введено минимум 4 символа, кнопка **`Establish Connection`** физически неактивна (`disabled`). Ошибки под полем не отображаются.

-   **Итог**: Валидация минимальной длины реализована исключительно через блокировку кнопки отправки. Пользователь не может отправить форму с невалидной длиной ни кликом мыши, ни клавишей `Enter`.

## 4. ⚙️ Логика работы

> ⚠️ **Важно: Контекст проекта**
> Данный проект является учебным и **не имеет серверной части (бэкенда)**. 
> Все процессы аутентификации, хранения пользователей и передачи данных эмулируются исключительно на стороне клиента (Frontend) с использованием `localStorage` и локальных конфигурационных файлов (`data.js`). 
> В реальном продакшн-проекте эти функции выполнялись бы на сервере.

-   Плейсхолдеры скрываются при наличии ввода и отображаются при пустом значении поля.

-   Состояние кнопки **`Establish Connection`** обновляется реактивно: она неактивна, пока `Callsign` < 3 символов или `Access Code` < 4 символов.

-   Ввод в поле **`Callsign`** фильтруется в реальном времени: блокируется ввод кириллицы (допускаются латиница, цифры и спецсимволы).

-   Ввод в поле **`Access Code`** фильтруется в реальном времени: допускаются только буквы латиницы, цифры и нижнее подчеркивание (`_`).

-   Аутентификация выполняется путем прямой проверки введенных данных с объектом `MOCK_USERS` из файла `data.js` (без обращения к внешнему API).

## 5. 🤖 Спецификация объекта MOCK_USERS: Логика аутентификации

-   **Источник данных:** Глобальный объект `MOCK_USERS`, объявленный в файле `data.js`.

-   **Назначение:** Эмуляция базы данных пользователей на стороне клиента. Не выполняет валидацию формата/длины — это ответственность UI.

-   **Структура данных:** Ключом объекта является позывной (например, `ORION`), а значением — объект с данными пользователя, содержащий поля `role`, а также позывной и ключ доступа (в data.js это `accessCode` и `fullName`, в user.json — `access_code` и `full_name`).

-   **Конфигурация валидных данных (для демонстрации):**

    -   Аккаунт 1: Позывной `ORION`, Ключ `NEBULA_7`, Роль `Commander`
    -   Аккаунт 2: Позывной `AURORA`, Ключ `COMET_42`, Роль `Specialist`

-   **Логика сравнения:** Возвращает `True` только если входной позывной найден в `MOCK_USERS` и введённый ключ доступа точно совпадает с сохранённым `accessCode`. Во всех остальных случаях — `False`.

## 6. 🔄 Обработка результатов аутентификации

-   **Успешная аутентификация:**

    -   **Условие:** Входные данные совпали с валидной парой из конфигурации.

    -   **Действие UI (Пошаговый UX-флоу):**

        -   Мгновенный отклик: При клике кнопка физически «проваливается» (визуальный эффект нажатия), меняет текст на `CONNECTING...` и начинает пульсировать. Повторные клики блокируются.

        -   Имитация задержки сети (3 секунды): В течение этого времени текст `Telemetry` остаётся в исходном состоянии (синий `> SYSTEM READY...`), создавая эффект «полёта сигнала».

        -   Успешное соединение: Ровно через 3 секунды текст `Telemetry` меняется на зелёный: `> CONNECTION ESTABLISHED. WELCOME, {ROLE} {FULL_NAME}`.

        -   Редирект: Данные пользователя сохраняются в `localStorage` (ключ `currentUser`). Спустя ещё 3 секунды (пауза для прочтения приветствия) происходит автоматический переход на главную страницу (Landing).

        -   Данные пользователя сохраняются в `localStorage` (ключ `currentUser`) для использования на последующих страницах.

-   **Неуспешная аутентификация:**

    -   **Условие:** Любая комбинация позывного и ключа доступа, кроме валидной пары из конфигурации.

    -   **Действие UI (Пошаговый UX-флоу):**

        -   Мгновенный отклик: При клике кнопка физически «проваливается», меняет текст на `CONNECTING...` и начинает пульсировать. Текст `Telemetry` остаётся в исходном синем состоянии (`> SYSTEM READY...`).

        -   Имитация задержки сети (3 секунды): Система «обрабатывает» запрос. В это время ошибки на экране нет.

        -   Появление ошибки: Ровно через 3 секунды сверху отображается блок `Auth Error Block` с текстом `️ Invalid callsign or access code`. Текст `Telemetry` меняется на красный: `> SYSTEM FAILURE. INVALID CREDENTIALS`. Кнопка возвращается в активное (яркое) состояние.

        -   Цикличность при повторной попытке: При повторном нажатии на кнопку блок ошибки мгновенно исчезает, телеметрия сбрасывается в исходный синий цвет (`> SYSTEM READY...`), и цикл (прожим → 3 сек ожидания → ошибка) повторяется. Система остаётся в этом цикле до тех пор, пока не будет введена валидная пара позывного и ключа доступа.

    -   **Примечание:** Сообщение об ошибке должно быть универсальным и не раскрывать, какой именно параметр неверен (принцип *security by obscurity*).

## 8. Визуальные требования

-   **Цветовая схема:** Тёмно-синий космический фон '#050816', голубые акценты '#4da6ff', белые текстовые элементы.

-   **Анимации:** 

-   Мигающий курсор в строке `Telemetry` (1s, step-end).

-   Пульсация радиоволн спутника (2s цикл, 3 волны с задержкой).

-   Свечение кнопки `Establish Connection` при наведении. Эффект применяется **только** когда кнопка активна (введено ≥ 3 символов в `Callsign` и ≥ 4 в `Access Code`). В состоянии `disabled` кнопка выглядит тусклой и не имеет эффектов при наведении.

-   **Карточка формы:** Полупрозрачный фон с `backdrop-filter: blur`, голубая рамка со свечением.

-   **Адаптивность:** Desktop-only (1024px+). Мобильная версия не предусмотрена.

| Поле Callsign | `login-callsign-input` |

## 10. 🌐 URL и маршрутизация

Так как проект является учебным и статическим (без серверной части), для локальной разработки и деплоя на GitHub Pages используются следующие адреса:

- **Local Base URL (Локальная разработка и тесты):** 
  - Главная: `file:///.../cassandra/index.html`
  - Авторизация: `file:///.../cassandra/login.html`

- **GitHub Pages URL (Публичный деплой):** 
  - Главная: `https://<username>.github.io/cassandra/`
  - Авторизация: `https://<username>.github.io/cassandra/login.html`
  *(Остальные страницы формируются аналогично, с обязательным суффиксом `.html`)*

> **Примечание для автоматизации:** 
> В конфигурационных файлах фреймворка (например, `config.py`) определяется базовый URL (`BASE_URL`) в зависимости от окружения. 
> Переход на конкретную страницу осуществляется путем добавления имени файла (например, `login.html`) к `BASE_URL`. Это гарантирует корректную работу тестов как на локальной машине, так и в CI/CD.
